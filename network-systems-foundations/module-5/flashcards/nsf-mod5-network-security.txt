What three properties define information security, and what does each mean?	<div style="text-align:left">Confidentiality → only the intended party can read it.<br><br>Integrity → data hasn't been modified or corrupted.<br><br>Availability → the data can actually be accessed.</div>	MSCS Network-Security Module-5
Module 5 maps three threats to three solutions. What's the mapping?	<div style="text-align:left">Data plane (traffic itself gets read) → IPsec.<br><br>Control plane (BGP routes get hijacked) → RPKI.<br><br>Application/transport (server gets impersonated) → TLS.<br><br>Same underlying tools (encryption, signatures, certificates) applied at a different layer each time.</div>	MSCS Network-Security Module-5
Symmetric vs asymmetric encryption — what's the core tradeoff?	<div style="text-align:left">Symmetric: one shared key, fast, scales to long messages.<br><br>Weakness → both sides need the key beforehand, and sharing it is the hard part.<br><br>Asymmetric: key pair, slow, limited to short messages.<br><br>Strength → the public half can be handed to anyone.</div>	MSCS Network-Security Module-5
Why does almost every real security protocol combine symmetric and asymmetric encryption instead of picking one?	<div style="text-align:left">Asymmetric encryption → used once, to exchange a session key.<br><br>Symmetric encryption → used for the rest of the actual conversation.<br><br>∴ get asymmetric's easy key distribution + symmetric's speed, without either one's weakness.</div>	MSCS Network-Security Module-5
Hash, MAC, and digital signature all "check" a message. What does each actually prove?	<div style="text-align:left">Hash → the message hasn't changed, if you already trust the digest itself.<br><br>MAC (Message Authentication Code) → the message hasn't changed, using a shared secret key, so a middle-man can't forge a new digest to match.<br><br>Digital signature → the message hasn't changed AND it came from a specific sender, using the sender's private key.</div>	MSCS Network-Security Module-5
What problem does a digital certificate solve, and what's its own weak point?	<div style="text-align:left">Binds a public key to an identity.<br><br>Weak point → on its own, an attacker can swap in their key and keep the identity fields unchanged.<br><br>Fix → a Certificate Authority signs it, so anyone can verify it wasn't tampered with, using the CA's public key.</div>	MSCS Network-Security Module-5
Trusting a CA (Certificate Authority) ultimately rests on trusting something. What?	<div style="text-align:left">The CA's public key itself.<br><br>Pre-installed in the browser or OS, not verified at connection time.<br><br>∴ the whole chain of trust for the internet's encryption bottoms out in a list of keys someone else decided to ship with your device.</div>	MSCS Network-Security Module-5
What does IPsec actually do, and where is it commonly deployed?	<div style="text-align:left">Creates an encrypted tunnel between two endpoints.<br><br>Can cover one machine or an entire site.<br><br>Most common real-world use → VPNs (Virtual Private Networks).</div>	MSCS Network-Security Module-5
Why does IPsec need Diffie-Hellman specifically, rather than just asymmetric encryption?	<div style="text-align:left">Goal → two sides with zero prior contact establish a shared secret over an insecure channel.<br><br>Nothing sent in the clear (p, g, and each side's public value) is enough on its own to compute the shared key.<br><br>Result → a session key neither side had to transmit directly.</div>	MSCS Network-Security Module-5
What is the BGP vulnerability that lets an attacker hijack traffic meant for someone else?	<div style="text-align:left">Any AS (Autonomous System) can announce any prefix, even one it doesn't own.<br><br>BGP has no built-in way to check the announcement is legitimate.<br><br>∴ a shorter fake path can simply outcompete the real one.</div>	MSCS Network-Security Module-5
How does RPKI (Resource Public Key Infrastructure) fix the BGP origin problem?	<div style="text-align:left">Origin validation, not path validation.<br><br>A signed ROA (Route Origin Authorization) ties a prefix to the one AS allowed to originate it.<br><br>Routers reject announcements whose origin AS doesn't match → doesn't stop a bad AS from lying about the path, only about ownership.</div>	MSCS Network-Security Module-5
Why are Regional Internet Registries a natural fit to act as the Certificate Authorities for RPKI?	<div style="text-align:left">RIRs (Regional Internet Registries) already allocate IP address space.<br><br>∴ the business relationship needed to verify ownership already exists, before RPKI is even involved.</div>	MSCS Network-Security Module-5
What does TLS (Transport Layer Security) actually add on top of plain HTTP?	<div style="text-align:left">Confidentiality, integrity, and authentication.<br><br>Sits between the application layer (HTTP) and the transport layer (TCP).<br><br>HTTP + TLS = HTTPS.</div>	MSCS Network-Security Module-5
What does the TLS handshake accomplish before any real data is exchanged?	<div style="text-align:left">Agrees on parameters (ciphers, algorithms).<br><br>Authenticates the server via its CA-signed certificate.<br><br>Establishes a session key for the encrypted traffic that follows.</div>	MSCS Network-Security Module-5
Let's Encrypt has no pre-existing business relationship with domain owners, unlike an RIR. How does it verify identity instead?	<div style="text-align:left">Domain ownership challenge, not a business relationship.<br><br>Prove you control the domain → put a specific value at a DNS record or a well-known HTTP path.<br><br>Let's Encrypt checks that value directly → issues the certificate if it matches.</div>	MSCS Network-Security Module-5

What are the three problems with plain HTTP over TCP?	<div style="text-align:left">• Messages are sent in <b>plain text</b><br>• Message <b>integrity</b> is not ensured<br>• No <b>guarantee</b> you are communicating with the server you expect</div>
Visiting chase.com, what three concrete mechanisms could land you at an attacker instead?	<div style="text-align:left">• <b>Modify packets directly</b> in transit<br><br>• <b>DNS responds with the wrong IP</b>, so the lookup itself is poisoned<br><br>• <b>BGP hijacking</b>, so even the correct IP address routes to a different destination</div>
What is TLS, what does it provide, and where does it sit?	<div style="text-align:left">A security layer between the application and transport layers. HTTP plus TLS is what HTTPS means.<br><br>It provides:<br>• Confidentiality<br>• Integrity<br>• Authentication</div>
Trace the chain of reasoning from the HTTP problems to digital certificates.	<div style="text-align:left">• <b>Symmetric encryption plus MACs</b> with a shared secret give confidentiality and integrity<br>&nbsp;&nbsp;<i>But how do we share the private key?</i><br><br>• <b>Asymmetric encryption</b> exchanges the session key, encrypted with the server's public key<br>&nbsp;&nbsp;<i>But how do we trust that public key is really the server's?</i><br><br>• <b>Digital certificates and CAs</b> bind the domain ownership to a public key, signed by a trusted source. This also supplies authentication.</div>
How does Let's Encrypt verify identity, and why can it not do what RPKI does?	<div style="text-align:left">RPKI's CAs are the RIRs, who already have a business relationship with the prefix owner. Let's Encrypt has no such relationship, so it proves <b>domain ownership by challenge</b>:<br><br>• Provision a <b>DNS record</b> under the domain, or<br>• Provision an <b>HTTP resource at a well-known URI</b><br><br>Let's Encrypt's servers fetch that location. If the expected value is there, ownership is proven and the certificate is signed.</div>
When does the TLS 1.2 handshake run, what does it accomplish, and in what message order?	<div style="text-align:left">Runs <b>after the TCP three-way handshake</b>. It agrees the parameters, authenticates the server, and sets up a private session key. Only then is encrypted traffic exchanged.<br><br><b>Client → Server</b><br>• Client Hello<br><br><b>Server → Client</b><br>• Server Hello<br>• Server Certificate<br>• Server Hello Done<br><br><b>Client → Server</b><br>• Client Key Exchange<br>• Change Cipher Spec<br>• Finished<br><br><b>Server → Client</b><br>• Change Cipher Spec<br>• Finished</div>
What do the Client Hello and Server Hello negotiate?	<div style="text-align:left">• The client states what it <b>supports and prefers</b>: encryption ciphers (DES, AES) and data integrity algorithms (SHA1, MD5)<br><br>• The server <b>picks</b> from that list and tells the client what it chose</div>
What does the Server Certificate message do, and how does the client check it?	<div style="text-align:left">• The server sends its <b>CA-signed certificate</b>, binding the domain name to the server's public key<br><br>• The client has a set of <b>root certificates</b> pre-installed in the browser<br><br>• If the certificate was signed by one of those CAs, the client accepts it and knows it has reached the domain it expected</div>
What happens in Client Key Exchange, Change Cipher Spec, and Finished?	<div style="text-align:left">• <b>Client Key Exchange</b> - the client picks a session key, encrypts it with the server's public key, and sends it<br><br>• <b>Change Cipher Spec</b> - signals the parameters are agreed and the next message will be encrypted<br><br>• <b>Finished</b> - a summary of every handshake message so far, proving none were tampered with. The server sends its own pair of these in return.</div>
What is mutual TLS (mTLS) and when is it used?	<div style="text-align:left">Normally only the client verifies the server, since the server does not care who the client is. In mTLS the <b>server verifies the client too</b>.<br><br>• Typical use: <b>access control for API endpoints</b>, letting in only explicitly allowed customers<br><br>• Browsers implicitly accept any certificate whose domain matches what is being visited<br><br>• Servers instead keep an <b>explicit access control list</b> of certificates they accept</div>
